# GeoVerse Map Server 服务分发与并发性能测试报告

> 测试日期：2026-07-30  
> 被测实例：`http://127.0.0.1:8080`  
> 代码基线：`e2f84de`（`feat(deploy): 补齐部署件与 -validate 配置自检`）  
> 服务版本：`v0.1.0-dev`

## 1. 结论摘要

- **服务分发契约通过**：黑盒探测 30/30 通过，覆盖发现、XYZ/WMTS、
  TileJSON、OGC API - Features、4 个空间算法、ETag、gzip、转发头、
  CORS、指标/管理端点及代表性 400/404/405/204 反例。
- **并发测试稳定**：35 个性能场景共完成 **441,216** 次请求、
  124.02 秒有效采样；所有响应均为场景预期的 2xx/3xx，**传输错误 0、
  5xx 0**。
- **当前机器的有效并发甜点区为 8–32**：热点切片在 c8/c32 分别为
  4,416/4,554 RPS；混合读取 c32 持续 30 秒为 **4,406 RPS，
  p95 8.72 ms，p99 9.90 ms**。提高到 c64/c128 几乎不增加吞吐，
  只会把 p95 提高到 19.81/33.08 ms。
- **未观察到持续内存增长**：30 秒 c32 持续流量前后工作集
  30.83 MiB → 26.29 MiB；全部测试结束并冷却后为 25.41 MiB。
- **发现两项缓存并发风险**：
  1. 同一冷瓦片没有请求合并：c32 的 64 个请求产生 32 次 miss；
     c128 的 128 个请求产生 66 次 miss。
  2. 空瓦片不做负缓存：同一个 204 瓦片在 3 秒内被请求 14,514 次，
     产生 14,514 次 miss、0 次 hit。

本报告是**本机回环、全内存 GeoJSON 示例数据**的基准，不是生产容量承诺。
PostGIS、磁盘缓存、MBTiles/GeoPackage、TLS、反向代理和网络 RTT 必须在目标
部署拓扑中另行复测。

## 4. 方法

### 4.1 契约探测

`bench/serveprobe` 使用 Go 标准库执行 30 项黑盒断言，包括：

- 转发头生成外部 HTTPS 链接；
- XYZ 与 WMTS 同一瓦片字节相等；
- PBF 无压缩/协商 gzip、ETag 条件请求返回 304；
- 超 zoom 返回 204，非法坐标 400，未知图层/要素 404；
- OGC bbox、分页和单要素读取；
- 4 个算法均执行真实请求并校验结果结构；
- Prometheus 指标、管理统计、CORS、方法边界；
- 当前 MCP 关闭状态诚实返回 404。

结果：**30/30 通过，耗时 20.61 ms**。

### 4.2 负载模型

`bench/servebench` 使用连接复用、完整读取响应体并记录端到端延迟，输出
RPS、状态码、传输错误、字节量和 min/mean/p50/p95/p99/max。

- 常规并发曲线：每档 3 秒，预热 20 次；
- 唯一冷瓦片：每档先清缓存，固定请求 512 个不重复 z6 坐标；
- 同瓦片冷启动：先清缓存，不预热，同时请求同一个 z0 瓦片；
- 混合读取：60% 热点切片、10% catalog、10% 要素、10% readyz、
  10% TileJSON；
- 持续测试：混合读取 c32，30 秒；
- 过载测试：混合读取 c128，5 秒。

客户端发送 `Accept-Encoding: gzip`。RPS 与字节吞吐均为本机回环测量值。

## 6. 性能结果

### 6.1 元数据、要素与探针

| 场景 | 并发 | RPS | p50 ms | p95 ms | p99 ms |
|---|---:|---:|---:|---:|---:|
| catalog | 1 | 1,994 | 0.53 | 1.00 | 1.19 |
| catalog | 8 | 3,994 | 1.84 | 2.70 | 3.25 |
| catalog | 32 | 4,063 | 7.63 | 10.40 | 12.88 |
| countries items，limit=100 | 1 | 173 | 5.62 | 7.47 | 8.24 |
| countries items，limit=100 | 8 | 914 | 8.52 | 10.93 | 19.44 |
| countries items，limit=100 | 32 | 1,287 | 24.32 | 32.02 | 38.30 |
| readyz | 32 | 4,378 | 7.12 | 10.07 | 11.70 |
| health | 32 | 4,972 | 6.36 | 8.04 | 11.23 |

`limit=100` 的 countries 响应约 171 KiB/次，c32 在回环上已输出
225 MB/s；生产环境更可能先受网络带宽影响。当前 4 个源全部是内存源，
`health` 的深检查近似空操作，所以它比 `readyz` 略快属于本次配置现象，
不能外推到 PostGIS。

### 6.2 切片、缓存与条件请求

| 场景 | 并发 | RPS | p50 ms | p95 ms | p99 ms | 状态 |
|---|---:|---:|---:|---:|---:|---|
| 热点 countries z2 | 1 | 1,970 | 0.53 | 1.01 | 1.17 | 200 |
| 热点 countries z2 | 8 | 4,416 | 1.71 | 2.44 | 2.90 | 200 |
| 热点 countries z2 | 32 | 4,554 | 6.84 | 8.05 | 8.76 | 200 |
| 热点 countries z2 | 64 | 4,418 | 14.25 | 17.24 | 18.62 | 200 |
| ETag 条件请求 | 32 | 4,075 | 7.62 | 9.29 | 10.77 | 304，0 B |
| 512 个唯一冷 z6 | 1 | 1,186 | 0.54 | 1.63 | 2.39 | 264×200 + 248×204 |
| 512 个唯一冷 z6 | 8 | 3,744 | 2.14 | 3.04 | 3.98 | 同上 |
| 512 个唯一冷 z6 | 32 | 3,429 | 8.83 | 11.00 | 17.38 | 同上 |
| 相同冷 z0，64 请求 | 32 | 1,226 | 18.79 | 48.33 | 50.72 | 200 |
| 相同冷 z0，128 请求 | 128 | 1,566 | 65.58 | 78.94 | 80.64 | 200 |
| 相同空 z6 | 8 | 4,835 | 1.67 | 2.33 | 2.75 | 14,514×204 |

唯一冷瓦片的每档 512 次请求全部是 cache miss；264 个非空结果进入缓存，
248 个 204 结果未进入缓存。热点切片在 c32 后吞吐不再增加。

### 6.3 空间算法

| 算法 | 并发 | RPS | p50 ms | p95 ms | p99 ms |
|---|---:|---:|---:|---:|---:|
| shortest_path | 1 / 8 / 32 | 1,988 / 4,512 / 4,383 | 0.53 / 1.72 / 7.04 | 1.01 / 2.40 / 9.31 | 1.18 / 2.78 / 10.45 |
| isochrone | 1 / 8 / 32 | 562 / 2,367 / 2,547 | 1.60 / 3.29 / 12.13 | 2.81 / 4.54 / 16.91 | 3.37 / 5.35 / 21.00 |
| map_match | 1 / 8 / 32 | 1,958 / 4,431 / 3,824 | 0.53 / 1.73 / 8.14 | 1.05 / 2.49 / 10.43 | 1.19 / 2.89 / 14.16 |
| dbscan | 1 / 8 / 32 | 1,414 / 4,045 / 3,873 | 0.55 / 1.98 / 8.15 | 1.11 / 2.72 / 10.28 | 1.54 / 3.11 / 11.94 |

等时圈是本组中成本最高的算法。除等时圈在 c32 仍有小幅吞吐增益外，
其余算法均在 c8 附近达到峰值，继续增加并发只会增加尾延迟。

| 场景 | 并发 | 时长 | 请求数 | RPS | p50 ms | p95 ms | p99 ms | 错误 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 混合读 | 16 | 5 s | 19,379 | 3,873 | 3.97 | 5.44 | 6.52 | 0 |
| 混合读 | 64 | 5 s | 19,488 | 3,887 | 16.11 | 19.81 | 25.73 | 0 |

## 7. 风险与瓶颈

### P1：同 key 冷 miss 未合并，存在缓存击穿

`serveTile` 的路径是 `cache.Get → source.Tile → cache.Set`，没有 keyed
singleflight。实测：

- c32、64 请求：32 miss + 32 hit；
- c128、128 请求：66 miss + 62 hit；
- 最终都只形成 1 个缓存条目，但 MVT 被重复生成数十次。

示例 GeoJSON 数据仍能承受；换成 PostGIS 后会把同一热点冷启动放大为并发
SQL、`ST_AsMVT` 和数据库连接占用。

**建议**：在 tile key 级加入请求合并；等待者共享首次结果/错误，同时正确
传播各自请求取消。补充 `coalesced_requests_total` 和 origin 生成耗时指标。

### P1：204 空瓦片没有负缓存

同一个空瓦片 3 秒内 14,514 次请求全部 miss，缓存条目始终为 0。地图边界
与低密度数据会产生大量 204，这会让源端重复做索引筛选。

**建议**：对 `ErrTileNotFound` 缓存短 TTL sentinel，并让
`DELETE /admin/cache` 同时清理；生产 nginx 已配置缓存 204，可作为边缘缓解，
但直连服务和未配置代理的部署仍需要保护。

### P2：高并发无背压，吞吐平台期后只增加尾延迟

混合流量 c32 与 c128 都约 4,406 RPS，p95 从 8.72 ms 升到 33.08 ms。
服务本身不做配额/限流，过量并发会在进程和上游数据源排队。

**建议**：当前机器先以每实例 8–32 活跃并发作为压测起点；在反向代理设置
连接/请求限额，并在 PostGIS 场景按连接池大小增加有界并发。最终阈值以目标
SLO 和生产拓扑复测为准。

### P2：大页 OGC 响应容易先打满网络

100 要素响应约 171 KiB，c32 回环输出约 225 MB/s。真实网络中 RPS 会显著
低于本机结果。

**建议**：客户端优先 bbox + 小页；在 nginx 对 GeoJSON 开 gzip/brotli；
压测报告同时观察字节吞吐而不是只看 RPS。

## 8. 建议的下一轮测试

1. **修复并复测缓存击穿**：同 key c32 的 origin miss 目标从 32 降为 1；
   204 重复请求在首次之后命中负缓存。
2. **PostGIS 真栈**：按 10 万、100 万、1000 万要素三级数据量测试动态 MVT、
   bbox 查询、连接池与数据库 CPU；加入数据库断连/慢查询反例。
3. **静态源矩阵**：分别对 MBTiles 矢量、MBTiles 栅格、GeoPackage 跑冷/热
   吞吐，验证不同 source 的 `Cacheable` 语义。
4. **生产拓扑**：Docker 资源限额 + nginx + TLS + 远端客户端；测 15 分钟
   稳态、突发、滚动重启和多实例分流。
5. **可选能力**：启用 API Key、MCP、磁盘二级缓存，做真实黑盒和重启后
   L2 命中测试。
6. **标准符合性**：在 S2 阶段引入 OGC API Features/WMTS 的 ATS/ETS，
   区分“声明支持”与“验证通过”。
